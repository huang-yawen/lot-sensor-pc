## 二、为什么这些改动不改变行为

| 点 | 说明 |
|---|---|
| `readSwitchStates` 统一成 2 值版（未识别值 → false） | 安全联锁本来就是 2 值版，一致；故障机原来是 3 值版（未识别 → null），但故障机只用 `states.pumpOn === true` 和 `!states.heatOn`，2 值 / 3 值结果完全一样 |
| `getTempDiff` 替换 `Math.abs(temp1-temp2)` | 原来每处都先判 `temp1!=null && temp2!=null`，`getTempDiff` 内部同样判，返回 null，外层加 `diff != null` 保护，等价 |
| `closePumpHeater` → `setSwitch` 循环 | `setSwitch` 内部动作（找配置 → 发 MQTT（带 d_no 判断）→ 存 t_direct → 记操作历史 source=interlock）与原内联逐句对应 |
| `cooldown` 工厂各持独立 Map | 与拆分前每模块一个 `lastFired` Map 完全等价 |
| `recordEvent` | SQL、字段、`nowLocalDateTime()` 取时间，与原来逐字一致；`code ?? null` 对字符串 code 无影响 |
| 合并 `resolveDeviceNo` 两次调用 | 两次解析的是同一个值，只是少一次 DB 查询 |

**唯一的非功能性差异**：`setSwitch` 会多打一行 `[ControlShared] xxx -> off（...）` 日志（故障机原来本地 `setSwitch` 不打日志）——只多日志，不影响逻辑。

## 四、还没动、需要你拍板的语义决策（R4 / R5 / R6）

这几项不是单纯去重，会改变"什么时候触发/触发后干什么"，属于设计取舍：

### R4：温差过大，4 处 4 个不同阈值配置项
| 位置 | 阈值项 | 动作 |
|---|---|---|
| 安全联锁 条件4 | `SAFETY_INTERLOCK.tempDiffThreshold` | 全关 |
| `ruleHeaterHysteresis` ③ | `temp_diff_open` / `config.tempDiffOpenThreshold` | 关加热 |
| `ruleDualTemp` | `dual_temp_diff` / `config.dualTempDiffThreshold` | 开泵 |
| 故障机 ⑤ | `temp_diff` / `FAULT_STATUS.tempDiffThreshold` | 进故障锁定 |

本次只统一了"怎么算温差"（`getTempDiff`），**没有合并这 4 个阈值项**。
要不要收敛成 1~2 个语义（如 `tempDiffWarn` / `tempDiffFault`）？需要你确认现场调参习惯。

### R5："没水流却加热 / 干烧"——4 套判据
安全联锁条件7（`heatOn && !pumpOn`）、`detectFaults` 干烧（`pumpOn && heatOn && flow<flowLow`）、
`ruleHeaterHysteresis` ②（`!pumpOn || flow===0`）、故障机 ③干烧（温度长时间不升）、④空转（`flow===0`）。
判据互不相同，是否统一（哪个为准）需要你定。

### R6："堵管"两套定义
- `linkageRules.detectFaults` 堵管：`pressure>pressureHigh && flow<flowLow`
- `faultStatus` ① `pipe_blockage`：`pressure<pressureLow || pressure>pressureHigh`（不看流量）
同名故障两套判据，触发时机不同。以哪个为准需要你定。

### R2/R3 深度合并（流量/压力"正常"判断）
`rulePumpAlwaysOn` 里判"流量正常"的口径（只查 `!=0 && <哨兵`）比 `isFlowNormal`（还查上下限）松。
本次没动规则内部判断——那是规则逻辑本身，收紧口径可能改变开泵时机，需要你确认。
